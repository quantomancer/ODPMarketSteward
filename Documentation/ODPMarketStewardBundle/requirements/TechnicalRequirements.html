3. Target architecture

ChatGPT conversation
Versioned MCP App component
Cloudflare MCP Worker
/mcp
Session Durable Object
FXLive API + optional OpenAI Responses API

ChatGPT selects a small read-only domain tool. The service uses the already verified governed bundle, validates the request, verifies the session disclaimer acknowledgement, retrieves permitted evidence from the fixed FXLive API, normalizes and validates it deterministically, and optionally asks GPT-5.6 to explain the already-calculated result. The app component renders the returned structured content and never talks directly to FXLive or OpenAI.

Request lifecycle

  1. Receive a Streamable HTTP MCP request at the stable public /mcp endpoint.
  2. Resolve a bounded MCP session object and require the startup-verified bundle.yaml, artifacts, versions, references, and digests.
  3. Validate the tool input against a standalone JSON Schema and the FX-35 value set.
  4. If acknowledgement is absent, return evidence mode NONE, the exact disclaimer, a session/policy-bound signed challenge, the validated pending request in component-only metadata for continuity, and the component without calling FXLive.
  5. After explicit user action, the component-only acknowledgement tool commits bounded policy state and returns ACKNOWLEDGED; the component then reissues the previously validated pending domain request, which the server validates normally.
  6. Fetch only the declared FXLive route with a timeout, size limit, and no-store behavior.
  7. Normalize the response, retain source timestamps, calculate deterministic metrics, and evaluate rules.
  8. Optionally call the OpenAI Responses API with a minimized evidence object after deterministic evaluation.
  9. Return concise content, model-useful structuredContent, and component-only _meta.

5. Architecture requirements

TR-ARCH-001Preserve service separationMust

The implementation shall deploy ODP Market Steward as a separate Cloudflare project and security boundary from FXLive.

  • Only the public HTTPS API joins the services.
  • No source KV binding, namespace identifier, deployment credential, or internal operational identifier is copied into the MCP project.
  • Each service can deploy and roll back independently.
TR-ARCH-002Use contracts as runtime inputsMust

The runtime shall load the bundle manifest first and resolve product, API, value-set, rule, monitoring, publication, and app behavior from the responsibility-owning artifact.

  • Required files remain within the bundle root and match their manifest digests.
  • Contract errors are typed and cannot be silently replaced by implementation defaults.
  • ODPS remains the product contract and is not treated as the API, execution, monitoring, AI, or presentation contract.
TR-ARCH-003Make deterministic evaluation authoritativeMust

Retrieval, parsing, decimal calculations, coverage checks, state classification, and hard verdicts shall execute in deterministic server code before any model explanation.

  • Model output cannot override a raw value, rule result, timestamp, state, or fitness verdict.
  • Failure of the optional model path leaves deterministic results available.
TR-ARCH-004Use UTC end to endMust

Parsing, calendar evaluation, freshness calculation, storage metadata, logs, test fixtures, and public output shall use UTC.

  • Public times are RFC 3339 UTC with trailing Z.
  • Deployment region, browser locale, and developer workstation timezone cannot change results.

6. MCP and ChatGPT App requirements

TR-MCP-001Expose current MCP transportMust

The service shall expose a public HTTPS Streamable HTTP MCP endpoint at /mcp.

  • Transport behavior follows the supported MCP SDK and Cloudflare Agents integration selected and pinned during implementation.
  • Legacy SSE is not the primary transport.
  • TLS, request size, timeout, concurrency, origin, and method behavior are explicit and tested.
TR-MCP-002Register a small typed tool surfaceMust

The server shall register five model-visible domain tools plus one component-only acknowledgement tool with unique verb-led names, narrow inputs, standalone JSON Schemas, exact outputs, and truthful annotations.

  • Unknown fields, arbitrary URLs, and instruments outside the exact 35-member value set are rejected.
  • All public tools declare securitySchemes: [{type: noauth}] and the compatibility metadata required by the pinned SDK.
  • The five domain tools are read-only; the hidden acknowledgement tool declares its bounded session-state mutation and non-idempotent replay behavior.
  • All market-data tools enforce the same acknowledgement and policy checks in server code.
TR-MCP-003Register a versioned UI resourceMust

The server shall register the market component under a cache-busting versioned ui:// URI with the MCP App HTML media type and associate it with every gated market-data tool.

  • Component metadata declares the least-privilege CSP and, for public distribution, a unique app domain.
  • The component uses the MCP Apps bridge for tool results and follow-up actions.
  • It never calls FXLive or the OpenAI API directly.
TR-MCP-004Separate result channelsMust

Tool results shall use content for concise narration, structuredContent for model-relevant facts, and protected _meta only for component hydration, signed acknowledgement material, or the bounded validated pending request used for post-acknowledgement continuity.

  • The pending request is not authorization and is validated normally when reissued.
  • The text and structured result remain sufficient when the component cannot render.
  • Secrets, credentials, internal identifiers, and unrestricted raw payloads are never returned.
  • Output is validated against the declared schema before transmission.
TR-MCP-005Return typed safe errorsMust

Protocol, policy, validation, dependency, and model failures shall return stable error codes, safe user guidance, and a correlation identifier.

  • Errors do not expose stack traces, keys, bindings, upstream private identity, or raw response bodies.
  • A failed market request never reuses stale in-memory data as if it were live.
TR-MCP-006Keep the public MVP authlessMust

The public, read-only MVP shall not require OAuth or a user account.

  • Disclaimer acknowledgement is a policy gate, not authentication.
  • If private accounts, entitlements, portfolios, or user-specific data are added later, a separate authentication and authorization design is required.

7. Data access and calculation requirements

TR-DATA-001Bind retrieval to OpenAPIMust

The FXLive adapter shall use ../interface/fxlive.openapi.yaml as the route, parameter, and response-shape contract.

  • The base URL is configuration-controlled and allowlisted; a tool argument cannot replace it.
  • Only declared GET routes are called.
  • Contract drift produces a typed validation result and operational alert.
TR-DATA-002Enforce the standard 35-instrument setMust

The server shall resolve allowed instrument membership exclusively from ../value-sets/fx35-instrument-set.yaml.

  • A standard-set snapshot contains exactly 35 unique members or is marked partial/incoherent.
  • Unknown, duplicated, missing, or additional identifiers are reported; they are not silently normalized into membership.
TR-DATA-003Normalize numbers safelyMust

OHLC values shall be parsed and calculated with the approved decimal strategy in ADR-003 and integer nanosecond timestamps shall avoid unsafe JavaScript number coercion.

  • Raw source values, canonical machine values, and rounded display values remain distinguishable in test evidence.
  • Open, high, low, close, change, range, body, basis-point, percentage, and ratio calculations follow versioned rule IDs in ../rules/ohlc-rules.yaml.
  • Calculations use 34 significant decimal digits; display rounding is ROUND_HALF_EVEN and occurs only at the presentation boundary.
  • JPY- and HUF-quoted prices and quote-currency deltas display 3 decimals, other governed FX-35 prices and deltas display 5, percentages and basis points display 2, ratios display 4, nonzero trailing zeros are retained, and rounded negative zero displays as 0.
TR-DATA-004Use bounded upstream requestsMust

Every call shall apply a deadline, maximum response size, JSON content validation, redirect policy, and finite retry policy appropriate to a read-only current-data request.

  • Retries do not extend beyond the approved user-facing latency budget.
  • Network and parsing failures preserve the exact attempt time and return evidence mode NONE unless an approved recorded fallback is selected.
TR-DATA-005Honor no-store live dataMust

Live FXLive responses shall not be written to Cache API, KV, Durable Objects, R2, analytics payloads, or application logs.

  • Only the explicitly allowlisted sanitized operational fields in operations/monitoring.yaml#/observability may be retained: non-reversible request correlation, tool/result/state categories, build and model-path states, aggregated counters, and sanitized dependency/request timings. No price, instrument, bar, raw upstream timestamp, or reconstructable market payload is retained.
  • Any telemetry snapshotId is a server-generated opaque non-reversible surrogate, not an upstream identifier or encoded market value.
  • Recorded evidence is a separate rights-gated workflow and cannot be created opportunistically from ordinary user calls.

8. Acknowledgement and runtime-state requirements

TR-ACK-001Issue a signed challenge before retrievalMust

When the current session lacks a valid acknowledgement, the server shall return the exact publication-policy disclaimer and a server-signed challenge without retrieving market data.

  • The signed material binds session identifier, policy version, disclaimer digest, nonce, issued time, and expiry time.
  • The component may retain the validated pending request for continuity, but it is not part of the authorization decision.
  • HMAC-SHA-256 or an equivalently reviewed server-side construction is used with a rotatable secret.
  • The maximum challenge lifetime is 600 seconds unless a stricter value is approved.
TR-ACK-002Use one strongly consistent object per server-owned MCP sessionMust

The implementation shall pin the Cloudflare Agents SDK Agent, createMcpHandler, and persistent WorkerTransport contract and use one Durable Object to serialize challenge issue, acknowledgement, replay rejection, and expiry for each server-issued opaque MCP session identifier.

  • The client cannot choose a business identifier as the Durable Object key; the Worker validates or creates the opaque MCP session identifier and maps it deterministically to the Agent namespace.
  • WorkerTransport state is persisted in the same Durable Object so a reconnect presenting the same valid unexpired server-issued session identifier reaches the same object and restores protocol initialization state; a missing, invalid, rotated, or expired identifier starts a new session and requires acknowledgement again.
  • The simpler McpAgent per-client-session pattern is not used for this guarantee because its documented state resets after that MCP session ends.
  • Application state is restricted to challenge and policy fields defined in FR-ACK-002, using the exact field names in the MCP application contract.
  • Alarm- or TTL-based cleanup removes expired state, and cross-session, reconnect, expiry, concurrent, and replay behavior is tested.
  • KV is not an acknowledgement-state substitute because replay-sensitive state requires strong per-session consistency.
TR-ACK-003Fail closed on acknowledgement errorsMust

Missing, expired, invalid, modified, replayed, or cross-session challenges shall return the canonical DISCLOSURE_REQUIRED result with a specific safe reason and shall perform no upstream retrieval.

  • A policy or disclaimer digest change invalidates prior acknowledgement.
  • Clock-skew behavior is bounded and tested in UTC.
  • The component-only acknowledgement tool returns ACKNOWLEDGED only after the Durable Object commits the transition, then the component reissues the previously validated pending market request for continuity; the server validates that call normally.
TR-STATE-001Implement the request workflow and total classifierMust

The runtime shall implement both the four-step request/evidence workflow and the separate total eight-branch service-state classifier in Functional Requirements Section 10 and the decision tables in the monitoring and rules artifacts.

  • Availability, service state, freshness, fitness, plausibility, provenance, and bundle validity remain separate fields.
  • Mandatory UNKNOWN/NOT_EVALUATED and catch-all parseable states map safely to UNKNOWN.
  • A health response alone cannot yield OPEN or FIT.
TR-STATE-002Separate requested and returned evidence modesMust

Requests use LIVE_ONLY or ALLOW_RECORDED_FALLBACK; results use LIVE, RECORDED, or NONE.

  • LAST_AVAILABLE is rejected until separately defined and governed.
  • Synthetic fixtures are available only to the test harness.
TR-STATE-003Use manual refresh in the MVPMust

The MVP shall refresh only after an explicit user or model tool action.

  • The component compares the prior and returned completed BarEnd and returns INITIAL, SAME_BAR, NEW_BAR, or NOT_EVALUATED when no comparison is possible.
  • Protocol and dependency failures use the typed error contract rather than a refresh outcome.
  • No background polling, timer loop, or hidden automatic upstream request is enabled in the first release.

9. GPT-5.6 integration requirements

TR-AI-001Call GPT-5.6 server-side and only when requestedMust

When includeStewardBrief=true, the Worker shall call the OpenAI Responses API with the current gpt-5.6 alias after deterministic assessment.

  • The OpenAI API key is a server-side secret.
  • The implementation records requested and returned model identifiers in sanitized evaluation evidence.
  • Model selection is configuration-controlled and covered by contract tests.
TR-AI-002Minimize and constrain model inputMust

The model receives only the bounded user purpose, relevant governed declarations, calculated metrics, typed rule results, UTC evidence times, and limitations required for the brief.

  • No full transcript, secret, source-private identity, unrestricted raw payload, or unnecessary personal data is sent.
  • A structured output contract distinguishes answer, evidence references, limitations, safe next step, and model metadata.
  • Schema-invalid or fact-changing output is rejected.
TR-AI-003Degrade without changing evidenceMust

A model timeout, rate limit, refusal, malformed result, or provider outage shall return the deterministic data and verdict with a typed Steward Brief state.

  • The model path has its own timeout and retry budget.
  • No fallback model is silently selected.
  • A failed brief cannot downgrade, upgrade, hide, or replace the deterministic result.

10. Security, privacy, and publication requirements

TR-SEC-001Apply strict input and egress controlsMust

The Worker shall validate MCP inputs before use and permit server-side egress only to the fixed FXLive origin and, for requested Steward Briefs, the OpenAI API.

  • URL, host, scheme, path, method, redirect, header, and instrument allowlists prevent SSRF and confused-deputy behavior.
  • Response content type, size, structure, and time fields are validated before processing.
TR-SEC-002Use a least-privilege component CSPMust

The component metadata shall declare only origins required by the compiled component.

  • No direct FXLive or OpenAI connection is permitted from the component.
  • frameDomains is omitted unless a separately approved embedded origin is essential.
  • Inline/eval behavior, external scripts, fonts, images, and styles are minimized and documented.
TR-SEC-003Protect secrets and challenge keysMust

Secrets shall be provisioned through Cloudflare Worker secrets or Secrets Store and accessed only by the server runtime.

  • Separate values are used per environment.
  • Rotation and revocation are documented and tested without source changes.
  • Build output, logs, errors, screenshots, video, and public bundles pass a secret scan.
TR-SEC-004Exclude restricted public identityMust

Public code, schemas, manifests, UI, logs shown in demonstrations, screenshots, video, and model responses shall use only identities permitted by policies/publication-policy.yaml#/identity/permittedPublicIdentities—ODP Market Steward, FXLive, and QMVP—and shall not disclose prohibited upstream provider identity or private operational identifiers.

  • The app name, product identity, organization identity, and competition title are used in their appropriate contexts rather than collapsed into one label.
  • A case-insensitive release scan covers public text and generated artifacts.
  • Sanitized errors use product-owned language rather than upstream implementation details.
TR-PRIV-001Minimize retentionMust

The service shall not retain prompts, transcripts, user profiles, account identifiers, precise location, or live market payloads.

  • Operational telemetry uses non-reversible correlation identifiers and aggregated status fields where possible.
  • A public privacy policy states actual collection, processing, retention, subprocessors, and deletion behavior before publication.
TR-PUB-001Enforce publication policy consistentlyMust

The exact versioned publication-policy disclaimer shall appear in the component and be acknowledged before first retrieval.

  • Tool text, structured output, component, listing copy, screenshots, video, and support materials preserve the MARKET DATA DEMO boundary.
  • No surface supplies trading advice, prediction, recommendation, ranking, order execution, or portfolio-specific guidance.

11. Operations and deployment requirements

TR-OPS-001Isolate environmentsMust

Local, staging, and production deployments shall use explicit Cloudflare configuration with distinct service names, URLs, Durable Object state, secrets, observability datasets, and optional R2 buckets.

  • Production never shares test acknowledgement state or synthetic fixtures.
  • Configuration files contain no secret values or provider-private identifiers intended for public release.
TR-OPS-002Expose safe health and readiness evidenceMust

A non-sensitive endpoint such as /healthz shall report service build/version and local readiness without retrieving market data or leaking dependency details.

  • Dependency health and deep diagnostics remain internal or authenticated operational evidence.
  • A healthy endpoint does not imply market availability, freshness, validity, or fitness.
TR-OPS-003Use reproducible deployment gatesMust

Deployment shall be built from pinned dependencies and blocked unless static checks, tests, bundle verification, prohibited-content scanning, secret scanning, and a staging smoke test pass.

  • Release evidence records source revision, build identifier, dependency lock digest, configuration target, UTC deployment time, and test result references.
  • No document claims success until the exact deployed endpoint has been exercised.
TR-OPS-004Support independent rollbackMust

The MCP Worker and app resource shall support rollback to the last verified compatible release without rolling back or changing FXLive.

  • Durable Object migrations are forward-safe and tested.
  • Tool schemas and versioned component URIs remain compatible with the rollback target.
  • Rollback evidence includes post-rollback MCP and ChatGPT smoke tests.
TR-OBS-001Collect sanitized operational telemetryMust

Workers Logs and Traces shall record request correlation, tool name, result code, evidence mode, state categories, dependency duration, model-brief state, and build version.

  • Telemetry excludes prompts, instrument payloads, secrets, full challenges, source-private identity, and user identifiers.
  • Retention, sampling, access, alert thresholds, and deletion are configured per environment.
  • Alerts distinguish MCP service failure, FXLive dependency failure, contract drift, Durable Object failure, and OpenAI dependency failure.
TR-R2-001Gate immutable recorded evidenceConditional

If and only if rights approval enables recorded fallback, an environment-specific private R2 bucket shall store immutable evidence objects and manifests.

  • Ordinary live requests do not write the bucket.
  • Object names are content-addressed or version-immutable, with content SHA-256, capture UTC, product, bundle, policy, and artifact versions, validation result, immutable manifest digest, and retention class.
  • Writes are create-only with a conditional non-existence precondition; overwrite and mutation of an existing evidence key are prohibited.
  • Public access is disabled; the MCP service returns only approved bounded evidence.
  • Lifecycle and any object-lock or retention mechanism are approved explicitly; deletion behavior follows the authorized retention policy.

13. Performance, reliability, and cost

TR-PERF-001Measure before setting service targetsMust

A deployed staging vertical slice shall measure Worker cold/warm latency, Durable Object operations, FXLive dependency time, deterministic evaluation time, component load time, optional model time, and end-to-end ChatGPT completion time.

  • Targets are approved only after representative measurements exist.
  • Model and non-model paths have separate latency budgets.
  • No unmeasured production performance claim appears in public material.
TR-REL-001Keep deterministic service available during optional dependency failureMust

The market-data and deterministic evaluation path shall not depend on GPT-5.6 availability, R2, or any unselected cloud resource.

  • FXLive unavailability returns a typed non-live result.
  • R2 unavailability cannot affect LIVE_ONLY requests.
  • Dependency circuit-breaking and retry behavior are measured and documented.
TR-COST-001Define a measured Cloudflare and model budgetMust

Before public release, measured usage shall support monthly and per-demonstration estimates for Worker invocations and CPU, Durable Object requests/storage, logs/traces, optional R2 operations/storage/egress, and OpenAI tokens.

  • Budgets, alerts, and abuse controls are configured from measured use rather than assumed free-tier capacity.
  • The optional model brief can be disabled independently without disabling deterministic tools.
