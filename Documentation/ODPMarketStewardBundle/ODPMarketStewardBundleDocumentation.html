Executive summary

The bundle corrects the architectural overloading identified in external feedback while keeping ODPS central to the product.

1ODP-family artifact claimed: ODPS
1companion standard: OpenAPI
5runtime project companion contracts
14package files including manifest
Outcome. ODPS describes the product and its commitments. OpenAPI describes the existing HTTP surface. The product-defined instrument set, runtime rules, monitoring, publication policy, MCP behavior, Functional Requirements Draft 0.3, Technical Requirements Draft 0.1, and migration traceability each have an explicit responsibility. Detailed Level Design Draft 0.1 translates them into non-normative modules, interfaces, sequences, test layers, release gates, and implementation work packages. The technical baseline selects a separate Cloudflare MCP Worker, a strongly consistent per-session Durable Object, a versioned MCP App component, sanitized Workers observability, server-side GPT-5.6 access, and rights-gated R2 only for optional recorded evidence.
Boundary. This is the proposed artifact set for the current draft scope, with unresolved decisions recorded instead of invented. It is not a decision-complete production specification, a complete ODP-family implementation, an ODPI certification, or proof that the Cloudflare MCP service, component, Durable Object, model integration, or R2 path has been implemented or deployed.

Artifact-by-artifact review

ODP standard

ODPS product contract

Contains the mandatory schema/version/product envelope, product identity, testing lifecycle, value proposition, use cases, conditional declarative SLA, declarative quality objectives, compact external-rule references, and API access metadata. It omits a product-strategy claim because the required higher-level KPI contribution was not supplied and must not be invented. Numeric version: 4.1 follows the published schema.

Companion standard

OpenAPI interface contract

Documents the exact Worker paths, both mutually exclusive /latest query modes, optional debug behavior, JSON/HTML outputs, errors, CORS, anonymous access, and Cache-Control: no-store. It says “latest stored,” not “live.” Raw stored timestamps are explicitly untrusted because the Worker forwards rather than enforces them; the governed wrapper rejects non-UTC-Z values.

Project companion

FX-35 controlled value set

Defines 35 unique alphabetically ordered symbols, base/quote decomposition, exact membership, count, notation, and ISO 4217 alignment. “FX-35” is explicitly product-defined, not claimed as an external industry standard.

Project companion

OHLC rules

Defines coherent snapshot assembly, required fields, projected FX-35 symbols, mathematical integrity, descriptive formulas, cross-bar continuity, freshness linkage, and purpose-specific fitness. Rule FAIL and availability INCOHERENT are separate. Closed-market, recorded, synthetic, and missing-evidence cases have explicit outcomes. Statistical plausibility remains NOT_EVALUATED while unconfigured.

Project companion

Monitoring profile

Defines UTC handling, authoritative-calendar requirements, inclusive two-minute freshness, availability and service states, evidence modes, cache age, recorded/synthetic separation, source-aligned no-store constraints, and observability. LIVE means current retrieval provenance; only LIVE + OPEN + freshness PASS permits a live badge. Calendar absence produces UNKNOWN.

Project companion

Publication policy

Contains exact demo wording, the requirement for explicit verifiable session acknowledgement, required surfaces, permitted public identities, UTC presentation, evidence labels, semantic accessibility requirements, and prohibited financial behavior. It delegates the signing and runtime mechanism to the app and technical contracts and makes data rights a release condition rather than pretending a disclaimer grants permission.

Project companion

MCP application contract

Defines five model-visible read-only domain tools plus one component-only acknowledgement action, bounded inputs, twelve standalone-schema materializations, a signed disclosure gate backed by bounded per-session state, public result modes LIVE, RECORDED, and NONE, six per-artifact validation layers, separate plausibility, manual component-identified refresh outcomes, a bounded server-side gpt-5.6 Steward Brief, the exact 35-value enum, the versioned MCP Apps resource, and an explicit reference to the separately authoritative technical delivery baseline.

Product-governance gaps intentionally not invented

  • License: public visibility is not a license; owner-approved usage terms are absent.
  • Data holder: legal entity, address, and accountable contact facts are not supplied.
  • Market calendar: no authoritative UTC adapter has been selected.
  • CreatedAt semantics: the Worker mapping is known, but producer-level semantic confirmation is pending. The field is nullable in governed snapshot evidence; missing or unconfirmed values force freshness to UNKNOWN rather than suppressing an otherwise valid bar.
  • Decimal presentation: deterministic decimal arithmetic is required; rounding mode and display precision remain unresolved.

OpenAPI documents that raw behavior, while the governed MCP adapter rejects any public evidence timestamp that does not parse as RFC 3339 UTC ending in Z.

ChatGPT-native MCP application contract

The app is designed as a small set of conversational powers, not as a financial terminal transplanted into ChatGPT.

User value

  • Know: retrieve latest stored completed-bar evidence and governed product metadata that base ChatGPT cannot fetch on its own.
  • Show: render an FX-35 market board with UTC intervals, availability, service state, quality evidence, and progressive detail.
  • Do: perform read-only deterministic domain evaluation. The only state mutation is the explicit component-only policy acknowledgement; the first release has no orders, execution, advice, or financial-system write action.

First-turn behavior

  • Explain the app’s role in one sentence and provide useful evidence immediately after acknowledgement.
  • Act directly on a complete request; ask no more than two essential clarifying questions when purpose is materially ambiguous.
  • Return control to the conversation after one bounded job and expose stable fields another tool or app can reuse.

Judging fit

The four equally weighted criteria are technological implementation, design, potential impact, and quality of the idea. The professional case is strongest when the demo proves one end-to-end question—“Can I use this observed FX product for one-minute descriptive analysis?”—with market evidence first, deterministic governance second, and a concise model explanation last.

Known gaps and release blockers

  1. Public HTML disclosure. The current Worker-generated root page lacks the mandatory MARKET DATA DEMO label and full disclaimer.
  2. Data rights. Public display, recording, redistribution, judge access, and attribution treatment require written confirmation.
  3. Calendar. No authoritative UTC market calendar is configured; session-dependent state remains UNKNOWN.
  4. CreatedAt. Producer-level semantics remain pending; governed freshness cannot pass until resolved.
  5. Decimal display. Rounding mode and display precision remain unresolved under FR-BAR-003.
  6. Plausibility. Lookback, sample size, and MAD threshold are unset; the only valid result is NOT_EVALUATED.
  7. License and accountable data holder. Owner-approved facts are not present and must not be invented.
  8. Application delivery. The separate Cloudflare MCP Worker, pinned Agents SDK version, Durable Object binding and migration, secrets, sanitized observability, Apps SDK component, public HTTPS endpoint, deployed standalone tool descriptors, privacy policy, support contact, unique app domain/CSP, and ChatGPT developer-mode tests do not yet exist.
  9. Worker validation. Stored fields are forwarded without governed validation, and the last array entry is assumed to be the selected bar.
  10. Cache policy. no-store prohibits persistent or cross-tool response caching; recorded evidence needs a separately authorized immutable capture mechanism.
  11. Unhandled exceptions. An uncaught storage or JSON failure may produce a platform-generated 500 outside the stable JSON error envelopes.
  12. OpenAPI publication. The contract is bundled but is not served from the Worker.

Implementation path

  1. Resolve blockers: data rights, public attribution treatment, accountable owner facts, calendar adapter, CreatedAt semantics, and decimal presentation policy.
  2. Align public Worker surface: add the exact demo disclosure to the HTML page, remove internal timing from public presentation, and decide whether to publish OpenAPI.
  3. Scaffold the separate Cloudflare application: create isolated development, staging, and production Worker configuration, Durable Object state and migration, Worker secrets, sanitized logs/traces, and safe /healthz; do not bind the source KV.
  4. Build the deterministic MCP vertical slice: load and verify the bundle, materialize all tool schemas, expose Streamable HTTP at /mcp, implement one selected bar and one versioned governed component.
  5. Implement the disclosure protocol: pin the Agents SDK Agent, createMcpHandler, and persistent WorkerTransport versions, map each server-issued opaque session identifier deterministically to one Durable Object, issue a signed session/policy-bound challenge, let the component-only acknowledgement tool commit the bounded state, reissue the previously validated pending request for continuity and validate it normally, guarantee zero upstream retrieval before acknowledgement, and test expiry, replay, reconnect, wrong-session, changed-policy, session-loss, concurrency, cleanup, and fabricated-token failures.
  6. Implement coherent FX-35 retrieval: metadata-before/after fan-out, bounded rollover reread, exact set enforcement, and no-store-compliant evidence handling.
  7. Implement rule and state engines: decimal calculations, hard validity, calendar-aware freshness, separated availability/service/fitness/plausibility states.
