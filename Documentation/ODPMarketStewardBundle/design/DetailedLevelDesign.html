1 · Executive design

Implementation outcome

The design resolves the requirements into one independently deployable Cloudflare service: an edge router exposes /mcp and /healthz, routes a service-issued opaque MCP session to one stateful Agent backed by a Durable Object, and executes a deterministic governed-data pipeline before any optional model explanation.

Input

Validated bundle artifacts, a bounded MCP tool request, explicit session acknowledgement for market retrieval, and point-in-time evidence from the fixed public FXLive API.

Output

Typed market board, instrument, movement, assessment, and product-discovery results with UTC evidence, source mode, quality findings, artifact pointers, limitations, and an optional grounded Steward Brief.

Benefit

Professional users receive useful market evidence first, then inspect why the result is available, coherent, valid, plausible, and fit—or why it cannot be claimed.

Users

Analysts, governance teams, and developers using ChatGPT as the conversational surface for the Market Data Demo.

Primary vertical slice. The first end-to-end implementation milestone is: connect the developer-mode app, request the market, render the exact disclosure without an upstream call, acknowledge through the component, retrieve a coherent FX-35 completed-minute board, show deterministic quality evidence, and refresh manually without mislabelling the same bar as new.

Non-goals for release 1

  • No trading advice, forecasting, opportunity ranking, order creation, execution, portfolio analysis, or user-specific entitlement.
  • No background polling, streaming ticks, hidden automatic refresh, persistent market-response cache, or LAST_AVAILABLE mode.
  • No direct component call to FXLive or OpenAI; no source KV binding; no D1, Queues, Vectorize, or Workers AI dependency.
  • No ODPG, ODPC, ODPV, or ODPR implementation claim. ODPS 4.1 remains the only claimed ODP-family artifact.
Evidence boundary. This document is a proposed implementation design. It does not prove that a Worker, Durable Object, MCP endpoint, component, OpenAI call, calendar adapter, recorded-evidence store, or production deployment exists or works.

4 · Runtime architecture

Stateful MCP coordination with deterministic evaluation

Trust boundaries

Boundary A — ChatGPT to MCP

All model and component input is untrusted. Validate standalone schemas, session headers, protocol version, content type, size, and tool visibility server-side.

Boundary B — MCP to source API

Only the configured origin, declared GET paths, known query values, bounded redirects, response sizes, and timeouts are allowed.

Boundary C — deterministic to model

Only minimized assessed facts cross into the optional model path. Output is schema-checked and fact-locked before inclusion.

Composition rule

The edge Worker is the only infrastructure composition root. Domain packages do not import Cloudflare, MCP, HTTP, OpenAI, or UI libraries. Tool handlers are thin adapters around application use cases. No McpServer or transport instance is shared globally across client sessions.

Cloudflare plan feasibility gate

Paid-plan decision required before the full-board implementation is called feasible. A first coherent FX-35 pass needs at least 37 external calls: metadata before, 35 bars, and metadata after. One complete rollover reread can take the total beyond 50 external subrequests, while the current Workers Free limit is 50 subrequests per invocation. The runtime also needs more startup/CPU headroom than should be assumed from a free-plan proof of concept. Staging must measure the selected plan and the exact pinned runtime before targets are approved.

The fan-out concurrency ceiling is six, matching the current simultaneous outgoing-connection limit. A lower configured value is allowed; a higher value is rejected at startup. The full-board rollover strategy is enabled only where the environment subrequest budget can cover its worst case. Otherwise, the request must return INCOHERENT rather than silently omit the required reread.

8 · Session and disclosure

Opaque session routing and component-mediated acknowledgement

Session identifier

The first MCP initialization without a valid mcp-session-id receives a cryptographically random, service-issued identifier. It contains no user, account, instrument, conversation, or business value. The identifier is integrity-protected so an arbitrary client string cannot select an Agent object.

oms1.<base64url random 128+ bits>.<base64url issued-at and expiry>.<base64url HMAC>
  • The router validates version, syntax, signature, issued time, expiry, and maximum length before calling getAgentByName.
  • The validated identifier deterministically names one Agent; WorkerTransport.sessionIdGenerator returns that same Agent name.
  • An invalid, expired, missing-on-a-non-initial request, or rotated identifier cannot be mapped to another existing object. The client must reinitialize and acknowledge again.
  • Exact session lifetime and clock-skew allowance require approval before coding; reconnect never extends expiry.

Reconnect and cleanup

  1. Same valid session ID routes to the same Agent and restores protocol initialization plus acknowledgement state.
  2. An interrupted market tool is retried as a new idempotent call; its result is not persisted for replay.
  3. Do not configure a persistent MCP event store in v1 because replay storage could retain live market results contrary to the no-store policy.
  4. The Agent alarm targets the approved MCP-session expiry, not the short-lived challenge expiry. 9 · Retrieval design

Fixed-origin, lossless, coherent evidence acquisition

Source request policy

Allowlist

HTTPS origin fixed by configuration and checked against the bundle; GET only; /health, /meta, /latest; only declared selectors; no arbitrary URL or debug mode.

Bounds

Per-call abort deadline, maximum bytes while streaming, expected JSON content type, redirect rejection, total tool deadline, and at most one transient retry within budget.

No-store

No Cache API, KV, Durable Object, R2, analytics payload, or cross-call memory cache. Request-scoped reuse and in-flight coalescing only.

Health operation semantics

getHealth is a bounded diagnostic operation, not part of the normal successful snapshot path and never part of the service's own /healthz. The assessment use case may call it once, after metadata or bar acquisition yields no usable market evidence, to distinguish a parseable reachable source service from an unreachable or unparseable dependency. A health response cannot establish market OPEN, freshness, bar coherence, availability of all instruments, or fitness. The call consumes the same dependency deadline and subrequest budget and its body is validated through RawHealthDto.

Coherent snapshot algorithm

  1. Read getSnapshotMetadata and validate its response; record target completed BarEnd.
  2. Retrieve each requested member through getLatestObservation in stable symbol order with a configurable concurrency of 1–6.
  3. Read metadata again after fan-out.
  4. Accept a coherent attempt only when metadata-before, metadata-after, and every accepted bar identify the same completed BarEnd.
  5. If the completed minute rolled during the request and the environment has enough subrequest budget, perform one complete bounded reread against the new target.
  6. If mismatch continues—or a required reread cannot safely run—return availability INCOHERENT. Never merge minutes or call the board complete.
async function assemble(instruments, ctx) {
  const before = await source.getMetadata(ctx);
  const bars = await mapConcurrent(instruments, ctx.concurrencyMax6,
    instrument => source.getLatestBar(instrument, ctx));
  const after = await source.getMetadata(ctx);

  if (sameCompletedBar(before, after, bars)) return coherent(before, bars);
  if (isRollover(before, after) && ctx.subrequestBudget.allowsFullRetry())
    return assembleOnceAgainstTarget(instruments, after.BarEnd, ctx);
  return incoherentAttempt(before, after, bars);
}

Lossless response parsing

Read the response body as bounded UTF-8 text. Do not call ordinary Response.json() for authoritative price or epoch processing, because standard JSON parsing converts number tokens to binary floating point. A pinned lossless JSON parser must preserve each numeric lexical representation, after which the normalizer:

  • converts OHLC lexemes to an arbitrary-precision decimal type;
  • renders Epoch as a non-negative decimal string without number coercion;

Common gated handler

async function runGatedTool(tool, rawInput, session, deps) {
  const input = tool.inputSchema.parse(rawInput);
  const ack = await session.acknowledgement(deps.policy.identity, deps.clock.now());
  if (!ack.valid) return deps.results.disclosureRequired(tool, input, session);

  const readiness = await deps.registry.readiness(tool.operation);
  if (readiness.state === "BLOCKED")
    return deps.results.contractUnavailable(readiness); // available after DLD-001

  const deterministic = await tool.useCase(input, readiness.snapshot, deps, {
    disabledCapabilities: readiness.state === "DEGRADED"
      ? readiness.disabledCapabilities : []
  });
  const result = deps.results.success(deterministic, tool.outputSchema);
  deps.telemetry.emit(deps.sanitizer.from(result));
  return result;
}

Error-contract blocker

Contract revision required before tool coding. Technical requirement TR-MCP-005 requires stable error codes, safe guidance, and a correlation identifier, but the current six output schemas contain only disclosure and success branches. Dependency, bundle, and internal failures therefore have no canonical schema-valid typed error representation. Before implementation, the application contract must either add a common ToolErrorOutput branch to the affected outputs or define an equally testable MCP protocol-error contract. Implementation must not invent an unadvertised error envelope.

The revision should distinguish at least INVALID_INPUT, INVALID_SESSION, CONTRACT_UNAVAILABLE, SOURCE_UNAVAILABLE, SOURCE_INVALID, OUTPUT_INVALID, MODEL_UNAVAILABLE, and INTERNAL_ERROR. The final vocabulary and HTTP/MCP mapping remain an application-contract decision.

Deliberate component coupling

Current OpenAI guidance supports separating data tools from render tools for some apps. Adding a render tool would change the six-tool contract, evaluation surface, and traceability. Reconsider only through a versioned requirements and application-contract change.

13 · Steward Brief

Optional model explanation after deterministic assessment

Only assess_fx_data_service may invoke the server-side model path, and only when includeStewardBrief=true. The requested API model is the configured gpt-5.6 alias; the result records the actual model identifier returned by the API instead of assuming it.

Bounded input

Allowed

  • Approved purpose and audience
  • Deterministic fitness and service/evidence states
  • Decisive rule results and artifact pointers
  • Calculated metrics required for the answer
  • UTC evidence times, declared limitations, and safe next steps

Prohibited

  • Full conversation transcript
  • Credentials, challenge or session values
  • Raw unrestricted source payload
  • Facts absent from deterministic evidence
  • Any instruction to forecast, recommend, rank, order, or execute

Generation and verification pipeline

  1. StewardBriefInputBuilder emits a small immutable JSON object with stable evidence IDs.
  2. A versioned lean prompt defines the role, fact boundary, prohibited behavior, required uncertainty, audience, and exact structured response.
  3. The Responses API call uses a server-side key, independent timeout, explicit model alias, bounded output size, and a measured attempt budget. No fallback model is silently selected.
  4. The response is schema-validated as StewardBriefResult.
  5. BriefFactValidator verifies every decisive pointer exists, every enumerated state matches deterministic evidence, and every number/date in the narrative belongs to an allowlisted fact set. Unknown factual tokens reject the brief.
  6. A valid result is GENERATED. Timeout or dependency failure is UNAVAILABLE; schema/fact/policy failure is REJECTED. Deterministic output remains unchanged in both cases.
Evaluation before optimization. Start with one attempt and a conservative timeout in staging, then measure usefulness, fact consistency, latency, and token cost. Any retry or reasoning-setting change is approved from representative evaluation evidence, not assumed.

Prompt versioning

Record promptContractVersion, requested model alias, actual model identifier, response-schema version, brief status, and evaluation-set version in sanitized evidence. Do not log the prompt, assessment payload, or generated answer. The optional model path can be disabled independently through configuration while all deterministic tools remain available.

Retry and deadline policy

  • All domain GETs are idempotent, but a retry is allowed only for approved transient network/status failures and only inside the total request deadline.

  • The model path has an independent attempt budget and cannot extend or cancel the deterministic result.
  • A global circuit breaker is not assumed. The selected v1 breaker mode—disabled, per-isolate advisory, or separately coordinated—must be measured and documented without storing market data or creating a global Durable Object bottleneck.

Criticality rule for bundle failure

Retrieval may continue after a non-critical governance validation failure only when the publication policy, disclaimer digest, MCP application contract, API allowlist, exact instrument set, and output schema remain verified enough to enforce safety.
