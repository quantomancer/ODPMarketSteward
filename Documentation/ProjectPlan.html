Delivery strategy and critical path

The sequence follows the DLD’s dependency-ordered WP00–WP11 model. Calendar commitments are deliberately not invented; estimates can be added only after dependency pins, staffing, rights, and representative staging measurements are known.

M0 — Ready to codeWP00 decisions and Definition of Ready approved
M1 — Governed vertical sliceWP01–WP03; package/profile and deterministic core
M2 — Working MCP serviceWP04–WP06; live adapter, session gate, six tools
M3 — Working ChatGPT AppWP07; versioned component and developer-mode evidence
M4 — Differentiated productWP08; grounded Steward Brief and paired evaluation
M5 — Operational candidateWP09 and G0–G6 evidence
M6 — Submission readyWP10, T9, G7, video, judge path
M7 — Optional recorded modeWP11 only after separate rights and policy approval

Critical path

WP00 → WP01 → WP02 → WP03 → WP04/WP05 → WP06 → WP07 → WP08 → WP09 → WP10. WP11 is outside the MVP critical path and must not delay a live-only submission.

First build increment: establish the external repository and pinned toolchain, compile the governed bundle into a runtime registry, then deliver get_fx_product_profile as a network-free contract-first vertical slice.

Mandatory automatic maintenance procedure

Standing instruction: whenever an agent performs material ODP Market Steward work, it must inspect this plan before acting and update it before the final response if a work item, decision, test, gate, risk, dependency, evidence reference or project status changed.
  1. Locate affected records. Map the request to one or more FDN/WP/DLD/T/G/R identifiers before implementation.
  2. Preserve boolean truth. Keep the checkbox unchecked and false for partial, blocked, failed, interrupted, sampled-only or unverified work.
  3. Require exact evidence for true. Verify artifact existence and non-emptiness, completed command/test exit, target environment, acceptance scope, UTC time and relevant digest or report before checking a row.
  4. Update comments. Replace generic status text with the exact outcome, evidence path/URI, UTC date, limitations and next blocker. Never erase useful history; move superseded detail into the change log.
  5. Update dependencies and risks. If new facts alter sequencing, ownership, safe states or release gates, update those records in the same change.
  6. Append one change-log entry. Record UTC time, affected IDs, what changed, validation scope and actor.
  7. Validate the document. Check unique IDs, local links, checkbox/data/text consistency, total rows, HTML structure and rendered first-page/readability scope before reporting success.
  8. Report precisely. State which rows became true, stayed false, or became blocked; never convert a design or recommendation into completed implementation.

The browser checkboxes are disabled because browser interaction does not persist to the controlled file. The HTML source is the single source of plan status.
